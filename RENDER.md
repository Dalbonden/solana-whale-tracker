# Deploying to Render (free plan)

Zero to running, assuming you have no Render account yet.

Render's free plan gives **750 instance-hours/month**. A calendar month is ~730 hours, so one always-on service fits — but *only* one. A second free service exhausts the shared budget and both get suspended.

---

## Before you start

You need three things, all free, none of them Render:

1. **A Supabase project** with the schema applied — see [DEPLOYMENT.md § 1](DEPLOYMENT.md).
2. **A Helius API key** — <https://dashboard.helius.dev>
3. **A Birdeye API key** — <https://bds.birdeye.so>

Have those keys in front of you; Render prompts for them during the deploy.

---

## 1. Push the repo to GitHub

Render deploys from a Git repo, so the code has to be on GitHub (or GitLab/Bitbucket) first.

```bash
gh repo create solana-whale-tracker --private --source=. --push
```

Or manually: create an empty repo on GitHub, then

```bash
git remote add origin https://github.com/YOU/solana-whale-tracker.git
git branch -M main
git push -u origin main
```

> Keep it **private**. Nothing secret is committed — `.env` is gitignored and only `.env.example` with placeholders is tracked — but there is no reason to publish it. See the note on GitHub Actions minutes in § 5 if you later make it public.

---

## 2. Create the Render account

1. Go to <https://render.com> → **Get Started**.
2. Sign up **with GitHub** — this authorises repo access in the same step, which you need anyway.
3. No credit card is required for the free plan.

---

## 3. Deploy via Blueprint

The repo contains `render.yaml`, so Render can configure everything itself.

1. Dashboard → **New +** → **Blueprint**.
2. Select your `solana-whale-tracker` repo → **Connect**.
3. Render reads `render.yaml` and shows one service, `solana-whale-tracker`, on the free plan.
4. It prompts for the values marked `sync: false`. Fill in:

   | Variable | Value |
   | --- | --- |
   | `HELIUS_API_KEY` | your Helius key |
   | `SOLANA_RPC_URL` | `https://mainnet.helius-rpc.com/?api-key=YOUR_KEY` |
   | `BIRDEYE_API_KEY` | your Birdeye key |
   | `NEXT_PUBLIC_SUPABASE_URL` | `https://xxx.supabase.co` |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase anon key |
   | `SUPABASE_SERVICE_ROLE_KEY` | Supabase service_role key |
   | `SOLSCAN_API_KEY` | leave blank if you don't have one |

   `CRON_SECRET` and `HELIUS_WEBHOOK_SECRET` are **generated by Render** — don't type anything for those.

5. **Apply**. First build takes 3–6 minutes.

You do **not** need to set `APP_URL`. Render injects `RENDER_EXTERNAL_URL` and `lib/config.ts` reads it at runtime — that is why webhook registration works without you knowing the URL in advance.

---

## 4. Verify

Your service URL appears at the top of the Render dashboard, like `https://solana-whale-tracker.onrender.com`.

```bash
BASE=https://solana-whale-tracker.onrender.com

curl -s $BASE/api/ping     # {"status":"ok",...}
curl -s $BASE/api/health   # integration report
```

`/api/health` should show `supabase: true`, `helius: true`, `birdeye: true`. If any is `false`, the variable is missing or misspelled — fix it in Render → **Environment**, which triggers a redeploy.

Open `$BASE` in a browser. The dashboard renders but is empty — nothing has been discovered yet.

---

## 5. Scheduling

Render's own Cron Jobs are a **paid** feature, so the scheduled work is triggered from outside. Two options.

### Option A — cron-job.org (recommended)

Free, unlimited, no minute budget, and short intervals keep the Render instance from spinning down.

1. Sign up at <https://cron-job.org> (free).
2. Grab your `CRON_SECRET`: Render → your service → **Environment** → reveal `CRON_SECRET`.
3. Create these jobs. For each, add a header `Authorization: Bearer <CRON_SECRET>`:

   | URL | Interval |
   | --- | --- |
   | `$BASE/api/cron/sync` | every 10 minutes |
   | `$BASE/api/cron/tokens` | every 2 hours |
   | `$BASE/api/cron/portfolios` | every 3 hours |
   | `$BASE/api/cron/discover` | every 6 hours |
   | `$BASE/api/cron/webhook-sync` | every 6 hours |

4. Set each job's timeout to the maximum (30s is the default and is too short — the request still completes server-side, but the scheduler will log a failure).

A 10-minute `sync` interval also solves the spin-down problem: Render sleeps a free service after **15 minutes** of inactivity, so a request every 10 minutes keeps it awake. At ~730 hours/month that stays inside the 750-hour budget, provided this is your only free service.

### Option B — GitHub Actions

`.github/workflows/cron.yml` is already in the repo. Add two repository secrets under **Settings → Secrets and variables → Actions**:

- `APP_URL` — your Render URL
- `CRON_SECRET` — from Render

**Read the minute budget before lowering the interval.** GitHub Actions is unlimited on public repos, but private repos get 2,000 minutes/month and *every run bills a minimum of one whole minute*:

| Interval | Runs/month | Verdict |
| --- | --- | --- |
| every 10 min | 4,320 | over budget |
| every 15 min | 2,880 | over budget |
| every 30 min | 1,440 | fits |

The workflow is therefore set to `*/30` and fans out to all five endpoints from a single job, gating the heavier ones on the clock. Do not lower it on a private repo.

The trade-off: a 30-minute interval is longer than Render's 15-minute spin-down, so the service **will** sleep between runs. Cold starts take ~50 seconds and Helius webhook deliveries that arrive during sleep are dropped. Use Option A if real-time alerts matter to you.

---

## 6. First run

```bash
CRON_SECRET=<from Render> node scripts/bootstrap.mjs https://your-service.onrender.com
```

Runs every job in dependency order — tokens, discover, sync, portfolios, webhook. Expect 5–10 minutes on the free instance, most of it in discovery.

Then reload the dashboard.

---

## Free-plan caveats, stated honestly

**Spin-down is the big one.** 15 minutes of no HTTP traffic and the instance sleeps; the next request takes ~50s to wake it. Consequences:

- Helius webhooks delivered while asleep are **lost** — Helius does not retry indefinitely, and the endpoint answers too slowly.
- The first dashboard visit after idle is slow.

Mitigation is Option A above: a 10-minute ping keeps it warm. Real-time alerting on a sleeping free instance is not achievable otherwise — that is a plan limitation, not a bug.

**512 MB RAM.** `next build` on this project is close to the ceiling. If the build OOMs, add an env var:

```
NODE_OPTIONS = --max-old-space-size=460
```

The runtime server idles well under the limit; it is the build that is tight.

**Job sizing.** `render.yaml` lowers `SYNC_WHALES_PER_RUN` to 12, `SYNC_TX_PER_WHALE` to 60 and `DISCOVERY_CANDIDATES_PER_RUN` to 40 — well below the Vercel defaults. The free instance is slow enough that the stock values risk overrunning. Raise them if you upgrade.

**One free service only.** 750 hours is a shared monthly budget. Adding a second free service means neither runs all month.

---

## Moving off later

Nothing here is Render-specific beyond `render.yaml`. `lib/config.ts` resolves the app URL from `APP_URL`, `RENDER_EXTERNAL_URL`, the Vercel production URL or `NEXT_PUBLIC_APP_URL`, in that order — so the same commit deploys to Vercel, Cloud Run or a plain VM without edits. Ask for a `Dockerfile` if you want the container path.
